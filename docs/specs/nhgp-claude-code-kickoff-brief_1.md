## 3. Build philosophy — read this before writing any code

- **Backend/architecture: designed for the full spec, from day one.**
  Database schema, module boundaries, and the permission model should be built to match the
  *complete* domain model in the EAS — not a stripped-down version that gets rebuilt later.
  Adding a capability in month 4 should mean extending existing structures, not replacing them.

- **Frontend/features: shipped in phases.**
  Only Phase 1 features (below) get built into working UI right now. Later capabilities
  (documents, inspections, finance, executive dashboards, AI assistant) get their schema/module
  scaffolding stubbed in but are not built out until their phase arrives.

- **Continuous delivery, not a big-bang launch.**
  The system goes live for the company after Phase 1 and keeps running. New capabilities get
  added to the live system incrementally — never a separate "v2" rebuild.

## 4. Phase 1 scope (target: 1–2 months, what gets handed to the company)

Build these end-to-end, working, deployed:

1. **Public property website** — browse/search published properties, property detail pages
   with photos and location
2. **Customer accounts** — register, log in, save favorites, submit inquiries/reservation
   requests
3. **Staff admin portal** — create/edit/publish properties, upload photos, manage inquiries,
   view and update reservation requests, basic role separation (Admin / Sales / Property
   Manager)
4. **Reservation tracking** — customer requests a property → staff sees it → updates status
   through the core lifecycle stages (Pending → Approved → Under Negotiation → Reserved),
   without the full inspection/legal-verification workflow wired in yet
5. **Basic email notifications** — registration confirmation, inquiry received, status updates

Everything else in the spec (Document Management, Inspections, Financial Recording, Executive
Intelligence, AI Services, full 13-persona permission matrix) is **out of scope for Phase 1**
but should be reflected in the database schema and module structure so it can be built onto
later without migration pain.

## 5. Role split — what Claude does vs. what the user does

**Claude owns:**
- All code — schema, backend, frontend, deployment config
- Technical architecture decisions within the agreed stack
- Maintaining two living files in the repo:
  - `PROGRESS.md` — what's built, what's stubbed, what's next
  - `SETUP.md` — a running checklist of exactly what the user needs to go set up, with clear
    instructions, updated as new needs come up

**User owns everything outside the code**, including but not limited to:
- Domain name registration
- Hosting accounts (app hosting, database hosting, file storage)
- Third-party API keys (email provider, maps, SMS, etc.) — Claude will say exactly which are
  needed and when
- Real company content (logo, brand assets, legal text, terms/privacy policy)
- Real property data to populate the platform before demoing to the company
- Real staff accounts (names/emails of who is Admin/Sales/Property Manager)
- Testing the live product from a user's perspective and giving feedback

**Working pattern:** talk → build → talk → build, in scoped single-task sessions (e.g. "build
the property CRUD API," not "build the whole platform"). Every session ends with committed,
working code pushed to the repo — the repo is the source of truth, not the chat history. This
means the project survives subscription gaps: if usage runs out or the subscription lapses,
picking back up is just opening the repo again and reading `PROGRESS.md`.

## 6. First actionable step

On the first real Claude Code session, opened inside the existing repo, ask Claude to:
1. Explore and summarize the existing repo structure, dependencies, and any existing Prisma
   schema (per Section 2)
2. Confirm/complete the Prisma schema for the Property, Customer, and Reservation domains,
   building on whatever already exists rather than starting fresh
3. Create `PROGRESS.md` and `SETUP.md` in the repo root
4. Begin with the Property domain: schema → API → one working admin page (list + create
   properties) before moving to any other feature

Do not attempt to build multiple capabilities in parallel. Finish one working vertical slice
before starting the next.
